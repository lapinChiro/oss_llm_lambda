# ローカル実機での動作確認

## トリガー

ユーザーが今回の変更の動作確認（実機）を依頼したとき。`/check-local` で明示的に呼び出す。

> 静的解析・自動テスト（lint / type-check / knip / test）は本 skill の範囲外。それは [quality-check](../quality-check/SKILL.md) の領分。本 skill は **実機での振る舞い確認** に専念する。

## ⚠️ 絶対遵守（最優先・例外なし）

**ローカル環境の起動（docker compose up）、migration、確認用データの作成は Claude（あなた）の仕事である。ユーザーに委譲・依頼・肩代わりさせてはならない。**

- ユーザーが「自分で実機確認する」と述べても、環境起動・migration・CLI probe を Claude が行う義務は消えない。目視の主体が誰であれ、環境準備は必ず Claude が完了させてから引き渡す。
- 「環境が無い／用意が要る／ユーザーに任せた方が早い」を、環境起動を省く理由にしてはならない。まず自分で `npm run docker:up` を実行し、health / OpenAPI / Todo probe まで済ませる。
- この項目は過去に繰り返し怠られた実績があるため、**最優先の遵守事項**として本 skill の全手順に優先する。着手時にまず本項目の充足（環境起動 + seed 完了）を確認せよ。

## アクション（計画 → 準備 → 実行 → 判定）

`.claude/rules/verification.md`（計画→実行→判定）に従う。

### 1. 確認項目の洗い出し（MECE）

今回の変更が影響する機能を特定し、確認項目を **正常系 / 異常系 / 境界値** で網羅的に列挙する。この 3 区分は最低限の floor であり、変更固有のリスクから確認項目を動的に追加する（[`coverage-floor-not-ceiling`](../../rules/coverage-floor-not-ceiling.md)）。各項目に **実行前に合否基準（期待結果）を定義** する。出力は表で管理する:

| 項番 | 操作 | 期待結果 | 実測 | 合否 |
|---|---|---|---|---|

### 2. 準備（あなたが全て行う）

**大原則: あなたが実行できることは、すべてあなたが実行する。** 環境の起動・migration・CLI で実行可能な確認は自分で進める。「ユーザーに任せた方が早い／確実」を理由に丸投げしない。ユーザーへ委譲してよいのは section 3 の **実機画面を通じた目視確認に限る**。

**委譲前プリフライト（3 点すべてを満たすまで section 3 へ進まない）:**

1. ローカル環境を **自分で docker compose 起動したか**（未起動のまま「環境が無い／用意が要る」を委譲理由にしない）。
2. CLI で実行可能な手順（probe / API 呼び出し / スクリプト）を **自分で実行し判定したか**（実行できるものをユーザーに代行させていないか）。
3. 残った「ユーザーへの依頼」が、本当に **実機画面の目視確認だけ** に絞り込まれているか（自動化可能な操作が紛れていないか）。

- 確認用 Todo は API/UI から一意な title で作成し、自分が作成した record だけを toggle/delete する。DB 全消去や無関係 row の変更を行わない。
- **ローカル環境の立ち上げは必ず docker compose のコンテナで行う**（backend / frontend を host 側 `npm run dev` で直接起動しない）。ホスト直起動はコンテナ実行時と環境（OS / ネットワーク / 依存解決）が乖離し、本番相当の確認にならないため:

  ```bash
  npm run docker:up
  docker compose -f docker/compose.yaml ps
  docker compose -f docker/compose.yaml logs backend
  ```

- **DB の隔離・スキーマ正当性を probe 前に検証する（assume しない）**: compose project/container、接続 DB 名、migration 成功、`todos` schema を確認してから結果を信頼する。他プロジェクトの PostgreSQL や stale `.env` へ接続していないことを確かめる。

- **挙動保存リファクタの before/after 実測で git 操作を baseline 取得に使わない**（`git stash` / `git checkout` は deny・`CLAUDE.md 行動規範` 参照）。この種の PRD では、**無改変で全緑の integration テストが byte レベルの before/after pin** そのもの（アサーションが before の期待値を符号化し、after のコードがそれを再生成 = 実 DB・fresh スキーマで検証）。実機 capture は **AFTER の smoke 確認**（正しいスキーマに対しリファクタ後コードが 4 経路等で意味ある応答を返す = runtime / dist 配線の健全性）に位置づけ、before/after の**値一致の主根拠は integration pin + 等価性分析 + mutation survivor** とする（AFTER smoke を主根拠に格上げしない）。

### 3. 私への依頼（実機画面の目視確認だけ）

私が行うのは **実機画面を通じた挙動の目視確認のみ**。それ以外（環境起動・CLI 実行・判定）は section 2 で全てあなたが終わらせる。CLI で実行できる確認をここに混ぜない。依頼は **一つずつ**、具体的な操作手順と「何が見えれば合格か」を添えて出す。

### 4. 判定

各項目を事前の合否基準に照らして判定し、表を埋める。正常系だけで完了とせず、異常系・境界値も必ず確認する。

## 制約

- 確認漏れのない計画を立ててから着手する（「とりあえず動かす」を禁ずる）。
- **backend / frontend は必ず docker compose のコンテナとして起動する**（host 側 `npm run dev` での直接起動は禁止）。確認環境をコンテナ実行時と一致させるため。
- ユーザーへ目視確認を依頼する前に、Frontend/Backend/PostgreSQL が healthy で実 API に接続していることを確認する。

## 禁止事項

- **CLI で実行可能なコマンド／スクリプト（probe・API 呼び出し・migration 等）をユーザーに代行させること。** 実行できるものは必ず自分が実行・判定する。委譲してよいのは原理的に自動化不能な実機画面の目視確認だけ。
- ローカル環境を **自分で起動せずに**「環境が無い／用意が要る」を理由に確認をユーザーへ丸投げすること。
- 外部依存（実トークン・実データ等）が絡むことを理由に、**自分で出来る部分まで含めて作業全体をユーザーへ渡すこと**（出来る部分は自分で進め、残った自動化不能操作だけを委譲する）。
- 正常系だけ確認して異常系・境界値の確認をユーザー任せ・未実施で完了とすること。

## 検証

- 着手後の操作履歴に、**自分による** `docker compose ... up` と CLI 確認（probe / API 実行）の実行痕跡がある。
- ユーザーへの依頼が、実機画面の目視確認（または対話的 OAuth ログイン等の自動化不能操作）のみに絞られている（CLI で回せる手順を含んでいない）。
- 確認項目テーブルが正常系 / 異常系 / 境界値を網羅し、各項目に事前定義の合否基準と実測・合否が埋まっている。
